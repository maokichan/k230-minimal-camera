# 机制为什么存在（给人类）

治理方案参照 cross-patch，守卫脚本参照 TuRead 的 Node 实现，为本项目裁剪后的最小集。假设不变：仓库的主要写入者包含 agent，而 agent 的失败模式是稳定的——上下文过期、把本机事实写进共享文档、文档无限膨胀、决定没有记录于是反复翻案。各部件对应防的病：

- **AGENTS.md 子树分治**——防"一个全局文件承载一切"：根入口只放指针与红线，细节在子树入口按需加载（渐进式披露）。
- **三守卫（pre-commit 门控链）**——防仓库变形：
  - docIndex：文档里写了路径 = 声明跟踪；链接方向只许平级/子一级；文档与现实脱钩给 notice。
  - repoGuard：绝对路径与密钥检出即拦——本机路径漏进共享文档，下一届 agent 会把它读进去当真甚至照着执行。
  - docGuard：行数上限逼出"细节下沉、旧口径退役"；入口文档短是结构性的，不是风格偏好。
- **决策笔记（.agents/notes/）**——防翻案：路径即元数据（生命周期目录 = 状态，迁移由提交史承载）；Alternatives considered 强制——记录决策而不记录它战胜了什么，等于邀请重新翻案。
- **trash/**——删除移入而非直接删，保留可恢复性。
- **无 identity 溯源门控**——git 本身承载提交身份（user.name/email），二次溯源是重复记账。

门控为纪律而设，不是安全机制：`--no-verify` 是人的绕行特权，agent 不用。
