# 决策：Rust 挂载点 —— CanMV + Rust 原生模块两步走

Status: implemented

前置决策见 [2026-11-07-技术路线-CanMV.md](2026-11-07-技术路线-CanMV.md)（板端固件选 CanMV 的论证）。

## Problem

用户希望板端程序写 Rust。但调研确认（docs/research/）：官方 CanMV 固件用户态只有 MicroPython；双系统 SDK 的 Linux 在小核 800MHz（无 RVV），MPP 多媒体栈在大核 RT-Smart 侧——"Linux 上写 Rust 直接调摄像头"不成立；裸机 Rust（andelf/k230-bare-metal 模板）做到 UART/GPIO 为止，无 VICAP/显示/KPU，且完整 TRM 无公开渠道。项目无硬性交付期限（闲置板子再利用，非比赛），"相机做出来"与"用 Rust 写"两个诉求都真实存在。

## Decision

两步走：

1. **第一步（基线）**：官方 CanMV 固件 + MicroPython 写 `src/main.py`（snapshot → JPEG → 存卡），先交付能拍照的相机。
2. **第二步（spike，与第一步并行）**：搭建 canmv_k230 固件自建环境（docker，参照 ref/canmv-k230-build.md），验证 Rust `riscv64gc-unknown-none-elf` staticlib 能否经 cbindgen 作为 MicroPython user C module 链入固件；spike 通过后，自定义计算内核用 Rust，相机胶水留 Python。

## Alternatives considered

- 纯 Rust（裸机或全 Rust 应用）：裸机被 TRM 缺失堵死在点灯阶段，与相机目标冲突；Linux 路线被大小核分工堵死。用户倾向纯 Rust，权衡后接受两步走。
- 纯 Python 不碰 Rust：交付最快，但 Rust 诉求被无限搁置；两步走的 spike 失败不影响第一步基线，风险可控。
- RT-Smart 侧独立 Rust 程序 FFI 到 MPP：RT-Smart libc/ABI 与 Rust target 的对齐无人趟过，比固件内嵌模块更深水。

## Consequences

- 第一步零风险：官方固件直接跑，50 行出片。
- 第二步引入固件自建链（工具链数 GB、docker 构建）与 ABI 对齐不确定性；改 Rust 需重刷固件，迭代慢于 Python。
- 固件构建产物与 Rust 模块源码的仓库归属（可能新增 firmware/native 子树）待 spike 后另立决策。
